// how it works

Three commands cover the whole workflow.

shipit reads your package.json, finds the build output and does the rest. There is no project to create first and nothing to click.

  1. 01

    shipit deploy

    Detects Astro, Vite, Eleventy, Hugo, a static Next export or a plain folder. Only changed files are uploaded, so the second deploy is faster than the first.

    $ shipit deploy › upload 3 changed · 211 unchanged ✔ live https://portfolio.shipit.page
  2. 02

    git push

    Connect the repo once with shipit link. From then on every branch you push gets its own URL, posted as a comment on the pull request.

    $ git push origin feat/dark-mode ↳ preview https://feat-dark-mode.portfolio.shipit.page
  3. 03

    shipit rollback

    Every deploy is kept, immutable. Going back points the domain at an older one. Nothing is rebuilt, nothing is re-uploaded.

    $ shipit rollback › production → d-2c09e4 (yesterday 18:42) ✔ rolled back in 0.31s

// preview urls

Every branch is a live link your reviewer can open.

Designers check the real thing instead of a screenshot. QA tests on a URL that matches production byte for byte. Delete the branch and the preview goes with it.

Previews are noindex by default and can sit behind a shared password.

0.31s

Shipped a typo to production? It is gone before you finish reading this sentence.

A rollback swaps a pointer at the edge. Old deploys stay cached in every region, so the previous version is served straight away.

No dashboard to learn. shipit --help fits on one screen, and that is the whole manual.
